# Decisions — NodeView Rendering Fix

---

## D1: バグ修正のアプローチ

### 決定
Phase 1で最小修正（285行目に1行追加）を行い、Phase 2で共通ラッパーへ統合。

### 理由
- ユーザー要件が「最小修正」であったため
- 既存のif/else if/else連鎖を大幅に書き換えるとリスクが高いため
- RAG知見では「保守的リファクタリング」を推奨していたが、既存要件を優先

### 代替案
- **全描画パスの再構築**: 新関数に全ロジックを移す → リスク高、既存要件と矛盾
- **Execution Map パターン**: 描画パスをオブジェクトリテラルで管理 → 大幅な構造的変更が必要

---

## D2: finalizeGroup 関数の実装

### 決定
引数チェック（`if (!g || !parentGroup) return null;`）を追加し、parentNodeチェックは省略。

### 理由
- `mainG.innerHTML = ''` により毎回流れがクリアされるため、二重追加のリスクなし
- RAG知見でも「二重追加防止チェックは不要」とされていた
- ただしnullチェックは将来の安全装置として追加（防御的プログラミング）

### 代替案
- parentNodeチェックを追加する — 移動防止の目的だが、現状では不要

---

## D3: テスト戦略

### 決定
ブラウザコンソール実行可能なテスト関数として実装（テストフレームワーク不使用）。

### 理由
- プロジェクトはビルドシステムなしのスタンドアランHTML/JS体制
- RAG知見の「3層テスト戦略」を参考にしたが、フレームワーク追加は既存要件と矛盾
- Browser Console API（`console.assert`, `console.group`, `console.table`）のみを使用

### 代替案
- Jest/Mocha/Playwright等のテストフレームワークを追加 — ビルドシステム導入が必要
